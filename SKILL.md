# E2E Test Plan

A comprehensive skill for defining and maintaining End-To-End (E2E) Testing Plans for web applications. Plans generated by this skill are designed to be executed by a testing agent using **Playwright** as the browser automation tool. The testing agent is assumed to have no prior knowledge of the project — it relies entirely on the plan's detailed steps and expected outcomes.

## What This Skill Does

This skill guides you through a systematic process to produce E2E testing plans that:

- Cover the entire project (or a user-defined subset of it)
- Document every workflow with its happy path and edge cases
- Provide step-by-step instructions a testing agent can follow blindly
- Specify expected outcomes and failure conditions for every step
- Define how authentication will be handled during test execution
- Define how discovered issues should be reported

The output is always one or more **E2E Testing Plan documents** (`.md` files) stored in an `.e2e-plans/` directory at the project root.

## When to Use This Skill

- User asks to "create an E2E test plan" or "end-to-end test plan"
- User wants to "map out workflows for testing"
- User wants "happy path and edge case definitions" for browser testing
- User asks to "update the test plan" or "add a workflow to the test plan"
- User wants to "review the E2E testing coverage" of the project
- User mentions "Playwright test plan" or "browser testing strategy"

## Prerequisites

- This skill only generates **plan documents**. It does not execute tests.
- The testing agent that will execute the plan requires Playwright (browser automation) tools.
- The project must be buildable and runnable (the plan needs URLs to target).

## Core Principles

1. **Zero-knowledge testing agent**: Every plan you generate must be usable by an agent that knows nothing about the project's internals. All workflows, steps, selectors, and expected behaviors must be documented explicitly. Never assume the testing agent "just knows" how something works.

2. **Test the user's perspective**: Workflows should reflect what a real user does — navigating pages, filling forms, clicking buttons, reading content — not internal implementation details.

3. **Separate plan from execution**: The plan is a static document. Any decision that must be made at test-execution time (e.g., "what credentials do I use?") should be encoded as a question the testing agent asks the user before starting.

4. **Happy paths first, edge cases second**: Always document the happy path completely before listing edge cases. Edge cases are expressed as deviations from the happy path.

## Process

### Step 1: Project Discovery

Before you can write a plan, you must understand the project as a real user would.

#### 1a. Scan the Codebase

Explore the entire project directory. Identify:

- **Project structure**: Is it a monorepo? Multi-service? Single app?
- **Subprojects with UIs**: Look in every directory for frontend projects (React, Vue, Angular, Svelte, etc.) — each one may need its own test plan.
- **Tech stack**: Read `package.json`, `tsconfig.json`, `vite.config.ts`, etc.
- **Dependencies**: Understand what frameworks and libraries are used.
- **Configuration**: Check for `.env.example`, `AGENTS.md`, `README.md`, `wrangler.jsonc`, and any other config that affects how the app runs.
- **Routing**: For web apps, understand the route structure. Look for router configuration files (e.g., React Router, Vue Router).

#### 1b. Map Capabilities

For the root project and each subproject with a UI, identify:

- **All pages/views/routes**: What URLs exist? What does each page do?
- **All user actions on each page**:
  - CRUD operations (Create, Read, Update, Delete)
  - Navigation (menus, links, tabs, breadcrumbs)
  - Forms (login, registration, checkout, search, filters)
  - Interactive elements (modals, toasts, drag-and-drop, file upload)
  - State transitions (loading states, empty states, error states, success states)
- **Workflows that span multiple pages**: E.g., checkout flow (cart → shipping → payment → confirmation)
- **Authentication and authorization**: Is there login/logout? Are there role-based views?

#### 1c. Learn How to Deploy

Find and document how to build and run the project locally:

- Install dependencies command (`npm install`, `yarn`, `pnpm install`)
- Build command
- Dev server command
- Any required environment variables (check `.env.example`, `AGENTS.md`, README)
- The local URL(s) the app runs on (e.g., `http://localhost:5173`)

Include this information in the test plan so the testing agent can start the app.

### Step 2: Ask User Intent

Before generating or modifying any plan, **ask the user what they want to do**. Present these options:

```
What would you like to do with the E2E testing plan?

1. **Create a new E2E test plan** — Generate a fresh plan for the entire project
   or a specific subproject. Scans the codebase and documents all workflows.

2. **Update an existing plan** — Load the current plan from .e2e-plans/ and
   modify it (add/remove/change workflows, steps, or edge cases).

3. **Add a new workflow** — Add a new workflow to an existing plan without
   regenerating the entire document.

4. **Review an existing plan** — Read the current plan and evaluate its
   completeness and accuracy against the actual codebase.

5. **Define a specific workflow** — Skip codebase scanning and let the user
   describe the workflow they want documented. Useful for planned features
   not yet implemented.
```

Wait for the user's response before proceeding.

---

### Step 3: Define Scope

Ask the user to define the scope of the testing plan:

```
What scope should this E2E test plan cover?

1. **Entire project** — All workflows across the root project and all
   subprojects with UIs.

2. **A specific subproject** — All workflows within a single subproject
   (e.g., only the admin dashboard, only the customer-facing store).

3. **A specific workflow** — A single workflow (e.g., "user registration",
   "product checkout"). Requires selecting which workflow.

4. **Multiple selected workflows** — Choose specific workflows from different
   parts of the project.
```

Base the options on what you discovered in Step 1. If the project has multiple UI subprojects, list them explicitly.

---

### Step 4: Define Authentication Strategy

If the project has authentication, **ask the user how the testing agent should authenticate during test execution**. This must be documented in the plan.

Present these options:

```
How should the testing agent handle authentication?

1. **Interactive** — The testing agent opens the browser to the login page,
   then asks the user to enter credentials manually.

   How this works at execution time:
   - The testing agent navigates to the login page
   - It asks the user (via text prompt): "Please log in to the application in
     the browser window. I will wait for you."
   - It monitors the DOM continuously using Playwright's page.waitForSelector,
     page.waitForURL, or a polling mechanism to detect when the login completes.
     Detection signals include:
     * A post-login element appearing (e.g., user avatar, dashboard heading,
       logout button, or a data-testid attribute like [data-testid="user-menu"])
     * The URL changing away from /login, /auth, /signin, or similar
     * A cookie or localStorage token appearing
   - The agent must set a reasonable timeout (e.g., 5 minutes) and prompt the
     user again if the timeout expires without detecting completion
   - Once login is detected, the agent proceeds with the test workflow

   Recommended when: credentials are sensitive, short-lived, or MFA is involved.

2. **Static (env file)** — The user provides credentials in a `.env` file or
   similar storage (e.g., `E2E_TEST_USERNAME=...`, `E2E_TEST_PASSWORD=...`).
   The testing agent reads the file, navigates to the login page, fills the
   form, and submits it automatically.

   How this works at execution time:
   - The testing agent reads E2E_TEST_USERNAME and E2E_TEST_PASSWORD from
     the .env file at the project root (or from environment variables)
   - It navigates to the login page
   - It fills the username/email field with E2E_TEST_USERNAME
   - It fills the password field with E2E_TEST_PASSWORD
   - It clicks the submit/login button
   - It waits for the post-login page to load (URL change or element appearance)
   - If login fails (stays on login page, sees error message), it reports the
     issue and stops

   Recommended when: testing credentials are stable, no MFA is required, and
   the user is comfortable storing credentials in a local file.

3. **No auth required** — The application has no authentication, or the tested
   workflows don't require it.
```

Document the chosen method in the plan's **Authentication Detail** section.
Include the specific DOM detection signals (selectors, URL patterns, etc.) the testing agent should use to confirm login completed.

### Step 5: Workflow Analysis

For the chosen scope, identify every workflow and analyze it.

#### Workflow Identification

List all workflows. A workflow is any end-to-end user journey that achieves a goal. Examples:

- User registration and login
- Browsing/filtering products
- Adding items to cart and checking out
- Creating, editing, and deleting a resource
- Admin user management

#### Happy Path Definition

For each workflow, document:

- **Preconditions**: What must be true before starting? (e.g., "User is on the homepage", "User is logged in")
- **Step-by-step actions**: Every click, type, navigation, and wait in sequence. Be explicit — the testing agent has no intuition.
- **Expected outcome for each step**: What should appear on screen? What state change should happen?
- **Final expected outcome**: How does the workflow end successfully?
- **Cleanup and restoration**: How to restore the system to its pre-test state after the workflow completes. If resources were created, specify how to delete them. If resources were edited or deleted, specify how to revert them. Prefer self-contained workflows where resources are created, exercised, and cleaned up in a single run so there is no residual state.

Format each step as:

```
Step N: [Action description]
  Action:        [e.g., Click "Add to Cart" button]
  Selector:      [e.g., button:text("Add to Cart") or [data-testid="add-to-cart"]]
  Input:         [If typing, what text to enter — or "N/A"]
  Wait for:      [Element, URL, or state to wait for after the action]
  Validate:      [What to check — element visible, text present, URL changed, etc.]
  Visual check:  [What to verify visually — layout, no overlapping elements, text not truncated, images loaded]
  Screenshot:    [true/false — whether to capture a screenshot at this step]
  Expected:      [e.g., Cart badge shows count of 1, toast notification "Item added"]
```

#### Edge Case Definition

For each workflow, identify edge cases as deviations from the happy path:

- **Empty states**: What happens when there are no items to display?
- **Invalid input**: What happens with malformed or incomplete form data?
- **Boundary conditions**: Maximum lengths, minimum values, pagination boundaries
- **Error responses**: API failures, network timeouts, server errors
- **Permission denial**: Accessing restricted resources without authorization
- **Concurrent operations**: Double-submitting forms, opening multiple tabs
- **Missing dependencies**: Required data or services not available

Format each edge case as:

```
Edge Case N: [Brief description]
  Happy step reference: [The happy-path step this deviates from]
  Variation: [What differs from the happy path]
  Action: [What the testing agent should do instead]
  Expected: [What should happen — this is often an error message or fallback UI]
```

#### Visual & Responsive UI Checks

Every workflow step that renders or updates a page MUST include visual and responsive checks. The plan must document:

- **Visual integrity**: What visual elements should be present and correct (headings, buttons, images, layout, colors)? The testing agent should capture a screenshot at key steps and verify the UI renders without visual defects — overlapping elements, broken images, misaligned content, text overflow, or missing elements.
- **Responsive breakpoints**: The testing agent MUST re-run the happy path of each workflow at every defined breakpoint to verify the UI adapts correctly:

```
Breakpoints to test:
- Desktop: 1280x720 (default)
- Tablet: 768x1024
- Mobile: 375x812
```

For each breakpoint, the testing agent must:

1. Resize the viewport to the target dimensions
2. Execute the workflow steps
3. Verify all elements remain accessible and properly laid out — no horizontal scrollbars, no truncated text, no overlapping elements, no off-screen content
4. Capture a screenshot for visual comparison

Edge cases (non-happy-path scenarios) can be tested at the default viewport only, unless the edge case is specifically about responsive behavior.

#### State Cleanup and Restoration

Every workflow that modifies data (create, update, delete) MUST document how to restore the system's state after the test. This ensures tests can be run repeatedly without accumulating stale test data or leaving the system in an inconsistent state.

**Important principle: the testing agent must leave the application in exactly the same state it found it.** If the test creates a resource, it must remove it. If it deletes a resource, it must restore it. If it edits a resource, it must revert the changes.

For each workflow, document:

- **What data is modified**: List the specific resources or state that change during the workflow.
- **Cleanup strategy**: One of the following, in order of preference:
  - **Self-contained (preferred)**: The workflow creates, exercises, and deletes a resource in a single run. E.g., creating a test product, editing it, viewing it, then deleting it — all in one workflow. This is the ideal pattern because it guarantees no residual state. Whenever possible, structure workflows so they pair create + edit + delete operations together in one self-contained flow.
  - **Paired teardown**: The workflow tracks what it created and explicitly deletes/reverts it at the end. Specify the exact steps to undo each change (e.g., "delete the created item", "restore the original name", "re-create the deleted item with the original data"). This is required when self-contained is not possible.
  - **Idempotent state**: The workflow operates on data designed to be ephemeral or self-cleaning (e.g., a session cart that disappears after checkout). No explicit cleanup needed.
- **Verification**: How to confirm cleanup succeeded (e.g., "Navigate to the product list and verify the test product no longer appears").

Format the cleanup section in each workflow as:

```
#### Cleanup

| Resource | Cleanup Action | Verification |
|----------|----------------|--------------|
| [Test product "e2e-item"] | Delete via product settings page | Product list no longer shows "e2e-item" |
```

### Step 6: Define Issue Reporting Strategy

**Ask the user** how the testing agent should handle issues discovered during test execution. Include this in the plan.

Present these options:

````
When the testing agent finds an issue during test execution, how should it be handled?

1. **Fix immediately** — The testing agent attempts to diagnose and fix the
   issue on the spot. Use this for obvious problems (e.g., broken CSS class,
   missing text, wrong selector). After fixing, the agent re-runs the affected
   step to verify the fix works.

2. **File an issue report** — The testing agent creates a detailed issue file
   in the `.issues/` directory at the project root. One file per issue, named
   `<workflow-name>-<kebab-case-description>.md`. The file must use the
   following GitHub-issue-like format so a coding agent can pick it up:

   ```markdown
   ---
   title: "[Workflow Name] - [Brief issue description]"
   workflow: "[Workflow Name]"
   step: [Step number]
   date: "[YYYY-MM-DD]"
   ---

   ## Description

   [What went wrong — 2-3 sentences]

   ## Steps to Reproduce

   1. [Step 1 from the workflow that led to the issue]
   2. [Step 2]
   3. [Step N — the failing step]

   ## Current Behavior

   [What actually happened — error message, wrong state, missing element, etc.]

   ## Expected Behavior

   [What should have happened per the plan]

   ## Screenshot

   ![Screenshot](data:image/png;base64,[Base64-encoded screenshot taken via
   Playwright at the moment of failure])

   ## Browser Console Errors

````

[Any console.error or console.warn messages captured during the failing
interaction]

```

## Suggested Fix

[Based on the plan generator's understanding of the codebase, suggest what
might be causing the issue and how to fix it. Include file paths and line
numbers if known.]

## Environment

- Browser: Playwright (Chromium)
- Viewport: [viewport at time of failure]
- URL: [URL where the issue occurred]
- Plan Version: [Version from metadata]
```

Note: The `.issues/` directory and its contents are git-ignored by default.
These files are intended as handoff artifacts for a coding agent.

```

### Step 7: Generate the E2E Testing Plan

Using all the information gathered in Steps 1-6, generate the plan document(s).

#### Plan Location

Plans are stored in `.e2e-plans/` at the project root:

```

.e2e-plans/
├── README.md # Index of all plans in this directory
├── ROOT.md # Plan for the root project (if it has a UI)
├── subproject-admin.md # Plan for the "admin" subproject
└── subproject-store.md # Plan for the "store" subproject

````

Each plan document follows the structure defined in `references/plan-template.md`. Load that file now to use as a template.

#### What to Include in Every Plan

Every plan MUST contain:

1. **Metadata**: Plan ID, version, date, scope, auth method
2. **Project Overview**: Brief description, how to deploy, URL(s)
3. **Testing Configuration**: Browser (Playwright), viewport, auth details
4. **Workflow Definitions**: Each with happy paths and edge cases
5. **Issue Reporting Instructions**: For the testing agent
6. **User Prompts**: Instructions embedded in the plan for the testing agent to ask the user about scope confirmation and issue handling at execution time
7. **Visual & Responsive UI Checks**: Breakpoints to test, what to verify visually at each step, and screenshot requirements
8. **Cleanup & State Restoration**: How each workflow restores the system to its pre-test state after execution

#### Multi-Subproject Plans

For monorepos and multi-service projects:
- Generate a **ROOT.md** plan only if the root project itself has a UI
- Generate a separate plan file for each subproject that has a UI
- Create a **README.md** index file that lists all plans and describes how they relate

---

### Step 8: Present and Review

After generating the plan(s), present the output to the user for review:

1. Show a summary of what was generated:
   - Number of plans created/updated
   - Number of workflows documented per plan
   - Total happy-path steps
   - Total edge cases
2. Ask the user to review the content. Show the actual plan content inline so they can read it.
3. If the user requests changes, update the plan(s) accordingly and repeat this step.
4. **Do NOT save the plan(s) to disk until the user explicitly approves.** Ask the user: "Would you like me to save this plan to `.e2e-plans/`?"
5. Only once the user confirms, write the plan file(s) to `.e2e-plans/` on disk.

---

### Step 9: Update Existing Plans

When the user asks to update an existing plan:

1. Load the current plan from `.e2e-plans/`.
2. Re-scan the codebase to identify changes (new workflows, changed pages, modified behavior).
3. Present the diff of what changed in the codebase.
4. Ask the user what specific updates they want.
5. Apply updates to the plan.
6. Present the updated plan for review. Show the actual changes inline.
7. **Do NOT save until the user explicitly approves.** Ask: "Would you like me to save this updated plan?"
8. Only once confirmed, write the updated plan to disk.

---

### Step 10: Review Existing Plans

When the user asks to review a plan:

1. Load the plan from `.e2e-plans/`.
2. Re-scan the codebase to verify accuracy.
3. Compare each workflow against the actual application behavior.
4. Report any discrepancies (e.g., "Step 5 says the button text is 'Submit Order' but it's now 'Place Order'").
5. Suggest updates if the plan is stale, and ask the user if they want you to apply them.
6. If the user asks for updates, apply them and present the updated plan for review.
7. **Do NOT save until the user explicitly approves.**

## Scripting Guidelines

If you need to write helper scripts (e.g., to scaffold a plan directory, validate plan structure, or generate an index), use **TypeScript** and the Node.js ecosystem only — no Python, Rust, or other languages.

Example:

```typescript
#!/usr/bin/env npx tsx
import * as fs from "node:fs";
import * as path from "node:path";

const plansDir = path.resolve(".e2e-plans");
if (!fs.existsSync(plansDir)) {
  fs.mkdirSync(plansDir, { recursive: true });
}
console.log(`.e2e-plans/ directory ready at ${plansDir}`);
````

Use `npx tsx` to run TypeScript scripts directly. Place any scripts in a `scripts/` subdirectory within this skill.
